# Alert Domain Specification (异常报警与事件中心规范)

## 1. 业务目标
异常报警与事件中心负责车辆实时安全监测、设备故障预警与电子围栏越界事件的全生命周期流转。核心能力包括：
1. 统一接收车载终端硬件传感器告警与云端规则引擎（如电子围栏）计算告警；
2. 规范化告警分类与严重度评级，执行毫秒级多租户定向广播（WebSocket）；
3. 提供严格的告警处置闭环有限状态机（待处理 -> 已处理 / 已忽略），并记录可追溯的审计日志；
4. 保证在多租户 SaaS 架构下告警事件严密隔离，禁止跨租户数据透出或越权处置。

---

## 2. 告警类型枚举 (`AlarmType`)

系统定义标准告警类型枚举，涵盖车载终端主动上报与云端规则引擎生成的安全事件：

| 告警代码 (`AlarmType`) | 告警名称 | 触发源 | 默认级别 | 典型触发条件与业务含义 |
|---|---|---|---|---|
| `LOW_BATTERY` | 蓄电池低电告警 | 设备上报 | `WARNING` | 车辆 12V 蓄电池电压低于 11.5V，有亏电无法启动风险 |
| `VIBRATION` | 停车异常震动告警 | 设备上报 | `INFO` | 熄火锁车后车载三轴加速度计检测到外力冲击，疑似剐蹭 |
| `OVERSPEED` | 车辆超速告警 | 设备/云端 | `WARNING` | 行驶速度超过预设安全时速阈值（如 > 120 km/h） |
| `POWER_CUT` | 主电源断开告警 | 设备上报 | `CRITICAL` | T-Box 外部主电源被非法切断，切换为内置后备电池，疑似盗窃 |
| `SOS` | 紧急求助呼叫 | 设备上报 | `CRITICAL` | 车内物理 SOS 按键被按下或气囊弹出触发重大事故呼救 |
| `TOW_AWAY` | 车辆异常拖移告警 | 设备/云端 | `CRITICAL` | 车辆在熄火未点火状态下产生持续位移且车速 > 15 km/h |
| `GEOFENCE_IN` | 驶入电子围栏告警 | 云端计算 | `INFO` | 车辆进入预设限定区域或重点监控园区 |
| `GEOFENCE_OUT` | 驶出电子围栏告警 | 云端计算 | `WARNING` | 车辆越界驶离允许运营区域或夜间禁出区域 |

## 3. 严重等级枚举 (`AlarmLevel`)

为指导运营中心和前端弹窗优先级，告警划分为三级严重度：

### 3.1 等级定义
- **`INFO` (提示级)**:
  - 业务含义：常规运营事件或微弱异常（如围栏驶入、低速轻微颠簸震动）；
  - 处置要求：无需立即人工干预，大屏与列表做静默提示，记录流水备查。
- **`WARNING` (警告级)**:
  - 业务含义：潜在安全隐患或违规操作（如超速、蓄电池电量过低、驶出围栏）；
  - 处置要求：APP 弹窗通知车主/车队管理员，建议在 24 小时内进行排查。
- **`CRITICAL` (紧急/致命级)**:
  - 业务含义：重大安全威胁或资产损失风险（如主电被拔、防盗拖车、SOS 紧急求助）；
  - 处置要求：监控大屏红色高亮警报并伴随声光提示，系统通过 SMS/语音网关即刻外呼，运维坐席必须在 3 分钟内介入响应。

## 4. 处置生命周期状态机 (`AlarmStatus`)

### 4.1 状态枚举
- `PENDING`: 待处理。告警刚生成时的初始状态。
- `PROCESSED`: 已处理。人工坐席或车主已核实并采取了应对措施（如确认正常施工、派遣拖车救援、联系车主等）。
- `IGNORED`: 已忽略。核实后判定为误报、传感器毛刺或无需跟进的轻微事件。

### 4.2 状态转移图
```text
           ┌──────────┐
           │ PENDING  │ (待处理)
           └────┬─────┘
                │
       ┌────────┴────────┐
       │ (核实已处置)     │ (核实为误报/忽略)
       ▼                 ▼
 ┌───────────┐     ┌───────────┐
 │ PROCESSED │     │  IGNORED  │
 └───────────┘     └───────────┘
   (终态·不可逆)       (终态·不可逆)
```

### 4.3 状态转移约束与规则
1. **初始状态确定性**: 所有新建告警记录（无论由 MQTT 上报或围栏服务生成）状态初始值必须为 `PENDING`；
2. **终态不可逆原则**:
   - `PROCESSED` 和 `IGNORED` 为系统终态；
   - 处于 `PROCESSED` 或 `IGNORED` 的告警禁止再次流转回 `PENDING`，亦不允许在两者之间互相修改；
   - 重复处置尝试将直接被 Repository / Service 层拦截并抛出状态冲突异常；
3. **处置留痕要求**:
   - 状态由 `PENDING` 转为 `PROCESSED` 或 `IGNORED` 时，必须强制记录：
     - `operatorId`: 执行处置的操作人用户 ID；
     - `processedAt`: 处置生效时间戳；
     - `remark`: 处置说明/备注原因（非必填或按策略校验）。

## 5. 告警上报报文与广播协议

### 5.1 设备端 MQTT 上报报文
- **Topic**: `/sys/{productKey}/{deviceNo}/alarm`
- **Payload 示例**:
```json
{
  "alarmType": "POWER_CUT",
  "alarmLevel": "CRITICAL",
  "timestamp": 1791448805000,
  "lat": 31.230416,
  "lng": 121.473701,
  "speed": 0.0,
  "message": "Main power supply disconnected, operating on backup battery",
  "details": {
    "voltage": 0.0,
    "backupBatteryLevel": 98
  }
}
```

### 5.2 WebSocket 实时推送协议
- **事件名称**: `alarm:triggered` (`WebSocketEvent.ALARM_CREATED` 或 `ALARM_TRIGGERED`)
- **广播房间路由规则**:
  - `tenant:{tenantId}`: 租户级监控总览大屏订阅，接收属于当前租户的所有告警；
  - `project:{projectId}`: 项目车队运营调度端订阅；
  - `vehicle:{vehicleId}`: 单车详情与跟踪页面订阅。
- **安全约束**: 严禁向未经认证或跨租户的客户端广播任何告警消息。

---

## 6. 多租户数据隔离防线

1. **存储行级隔离**: 所有告警表记录必须包含 `tenant_id`、`project_id`、`vehicle_id` 与 `device_no`；
2. **上下文强约束**: `AlarmRepository` 内部所有 `find`、`list`、`updateStatus` 操作必须严格提取 `TenantContext.getTenantId()` 进行约束；
3. **越权防御**: 若用户试图处置不属于当前租户的告警 ID，系统直接返回 404（资源不存在）或抛出安全越权异常，绝不泄露其他租户的告警数据与存在性。
