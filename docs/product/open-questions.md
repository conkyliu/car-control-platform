## 1. 核心业务差异与裁决记录 (Decisions Log)

### 决策 1：多租户与多项目数据上下文传递机制
- **背景/分歧**：功能清单第 21 模块（项目管理）与第 22 模块（多租户架构）均要求数据隔离。在 HTTP 请求中，是依靠 URL Path（如 `/tenants/:id/projects/:pid/devices`）还是依靠 Request Header？
- **裁决结果**：
  - **租户上下文**：统一使用请求头 `x-tenant-id: <tenantId>` 进行传递。超管可通过 Header 切换当前选中的租户；普通用户则自动绑定登录所得租户。
  - **项目上下文**：统一在列表查询 Query 参数（如 `?projectId=proj_001`）或可选头 `x-project-id` 中传递。
- **代价与收益**：避免了前端大量繁琐的嵌套路由重写，后端拦截器 `TenantContext.run(...)` 能够统一切面注入租户环境。

---

### 决策 2：双 Token 无感静默刷新生命周期
- **背景/分歧**：功能清单 1.5 提出“双令牌机制”。AccessToken 900 秒 (15分钟) 过期，RefreshToken 7天有效。当用户正在填写表单时 AccessToken 过期，如何保证用户不被强退？
- **裁决结果**：
  - 前端 HTTP Client 在收到 401 Unauthorized 响应时，不立即弹窗登出；
  - 启动单飞互斥队列 (`refreshPromise`)，自动调用 `POST /api/v1/auth/refresh` 换取新令牌；
  - 换票成功后，使用新 Token 自动重发原请求，对上层视图组件完全无感；
  - 仅当 RefreshToken 本身也失效或被后端注销时，才触发强制登出并清空 LocalStorage。

---

### 决策 3：远程车控安全分级与二次确认 (L1 / L2 安全门禁)
- **背景/分歧**：功能清单 6.11（防误触二次确认）与 6.13（安全码校验）提出控车安全要求。所有控车指令是否都需要输密码？
- **裁决结果**：
  - **L1 常规指令**（门锁、寻车鸣笛、双闪、座椅加热、升降车窗）：仅弹出 Ant Design 6 确认对话框，展示目标车牌号与指令意图，点击“确认执行”即可下发；
  - **L2 高危指令**（远程点火启动、远程熄火、长途解锁）：弹出带 6 位数字安全密码（或管理员二次验证 Token）输入的 Modal 弹窗，校验通过后才向后端发送包含 `securityCode` 的 payload。

---

### 决策 4：OTA 固件升级前置安全门禁与前端拦截
- **背景/分歧**：后端 Gate 5 AC-3 与 ADR-013 强制要求：车辆点火行车中 (`engineRunning === true`) 或蓄电池电压低于 12.0V (`batteryVoltage < 12.0`) 时严禁执行 OTA。
- **裁决结果**：
  - 后端作为最终安全底线（若违规，任务状态跃迁为 `SKIPPED_UNSAFE` 并记录原因）；
  - 前端在 OTA 计划选车与执行向导界面中，提前调取选中车辆的实时车况，对处于“行车中”或“低电压 (<12V)”的车辆以黄色 Alert 警示高亮，并在批次下发前提示预计跳过的台数，避免运维人员产生“为什么升级失败”的困惑。

---

### 决策 5：历史轨迹回放性能与矢量抽稀
- **背景/分歧**：功能清单 10.2 要求支持历史轨迹回放。高频上报的车辆若查询 7 天历史轨迹，点位可能超过数万个，直接在浏览器地图绘制会导致严重卡顿甚至崩塌。
- **裁决结果**：
  - 前端调用后端 `GET /api/v1/locations/trajectory` 时，默认传参 `tolerance=0.0001` 启用后端的 Douglas-Peucker 矢量抽稀算法，将冗余直线点压缩 80% 以上；
  - 前端使用 Canvas / AMap 矢量折线渲染，配合定时器帧率平滑插值移动小车 Marker。
