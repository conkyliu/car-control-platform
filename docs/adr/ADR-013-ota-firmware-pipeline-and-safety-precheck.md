# ADR-013: OTA 固件全生命周期流水线与行车安全前置检查决策

## 背景
车载固件 OTA 升级（Over-The-Air）直接涉及车辆核心零部件（如车载 T-Box、中央网关 Gateway、域控制器及底盘/车身 MCU）的底层固件擦除、Bootloader 烧录与系统重启。与消费级移动设备（手机、平板）的软件更新相比，车载 OTA 具有极端严苛的安全与物理风险特征：
1. **行车安全物理红线**：
   - 固件刷写过程中，芯片处于调试烧写模式，CAN/车载以太网总线通信完全中断，外设控制器失联；
   - 若车辆在行驶状态（Engine On / ACC On / 具有行驶速度）下发生固件更新与系统重启，将瞬间导致动力输出中断、电子转向助力丧失、制动防抱死系统失效或数字仪表黑屏，极易引发车毁人亡的恶性交通事故；
2. **12V 蓄电池亏电与硬件变砖风险 (ECU Bricking)**：
   - 固件刷写过程通常持续数分钟，车辆熄火时发电机不工作，全靠车载 12V 蓄电池供电；
   - 固件写入与擦除属于高功耗操作。若蓄电池本身电量偏低（电压低于 12.0V），刷写过程中的大电流负载极易拉低供电总线，触发单片机欠压复位（Brown-out Reset, BOR）；
   - 擦写过程中途掉电将造成 Flash 分区损坏或引导程序扇区擦除不全，导致硬件“彻底变砖”，车辆无法再启动，必须通过拖车返厂拆机维修，带来巨额售后成本与品牌声誉损失；
3. **单侧防线失效风险与固件篡改威胁**：
   - 传统方案仅依赖车载终端本地做简单检查，但若老版本固件本身存在传感器逻辑缺陷、或者因网络传输遭到中间人篡改/CDN 缓存污染，缺乏云端多层前置门禁将造成灾难性后果；
   - 在多租户车联网架构下，若缺乏车型版本兼容校验与租户隔离，容易发生跨车型误刷错刷。

---

## 决策
1. **建立权威双重安全前置检查门禁 (Two-fold Safety Pre-check Gate)**：
   - 在批次调度器向设备下发升级指令之前，云端强制调用 `OtaSafetyService` 检索车辆当前运行状态与 Redis 实时遥测缓存 (`telemetry:latest:{vehicleId}`)；
   - **熄火与静止强校验 (Engine Off & ACC Off & Zero Speed)**：
     - 必须满足 `engineRunning === false`、`accStatus === false` 且速度 `speed === 0`（或 $< 0.5\text{ km/h}$）；
     - 任何点火状态、钥匙通电或非零车速车辆，坚决禁止下发；
   - **蓄电池电压安全门禁 (Battery Voltage $\ge 12.0\text{V}$)**：
     - 必须满足最近一次有效上报的 12V 蓄电池电压 $\ge 12.0\text{V}$。低于 12.0V 判定为亏电高危状态，拒绝下发；
   - **遥测时效性保鲜期约束 (Freshness Window)**：
     - 上述遥测状态时间戳与当前调度时刻差必须 $\le 15$ 分钟（$900,000\text{ ms}$）。若车辆长期待机无遥测或数据过期，视为状态未知，安全判定不通过。
2. **设计非阻塞式安全拦截状态 (`SKIPPED_UNSAFE`)**：
   - 安全前置校验未通过的设备升级任务，云端状态机直接将其置为终态 `SKIPPED_UNSAFE`，不产生 MQTT 下行下发；
   - 结构化记录拦截原因代码（如 `REASON_ENGINE_RUNNING`、`REASON_LOW_VOLTAGE: 11.4V < 12.0V`、`REASON_TELEMETRY_STALE`）；
   - **非阻塞原则**：被跳过的车辆不阻塞当前批次中其他通过校验的合规车辆，调度流水线继续平稳推进；
   - 处于 `SKIPPED_UNSAFE` 的任务支持在后续车队巡检周期或车辆熄火充足电后，由人工或补偿调度任务重新排期。
3. **固件防篡改双哈希流水线 (Dual Hash Integrity Pipeline)**：
   - 固件在发布登记时，云端服务必须计算并严格校验其 64 位十六进制 SHA-256 校验和（可辅以 MD5 校验和）；
   - 下行升级通知报文（`/sys/{PK}/{Dev}/ota/upgrade`）强绑定 `checksumSha256`；
   - 设备端在分片下载完成后的 `VERIFYING` 步骤中，必须在 RAM 或暂存分区对固件包执行整体 SHA-256 哈希计算；
   - 哈希值必须与云端下发值完全一致，方可进入 `FLASHING` 步骤；若哈希不匹配，设备立即上报 `FAILED` 并清空暂存区，杜绝恶意篡改或损坏包写入执行分区。
4. **多租户隔离与全链路审计留痕**：
   - 固件包严格限制在 `tenant_id` 范围内，且与 `targetModelId` 强绑定，严禁跨租户或跨车型下发；
   - 固件发布、计划创建、下发调度、安全拦截 (`SKIPPED_UNSAFE`) 均完整记录操作人 `operatorId`、时间戳与环境上下文，写入系统审计日志。

---

## 结果
- **行车安全绝对兜底**：从云端架构源头消除了在行驶中触发刷写造成动力总成中断的致命隐患；
- **消除亏电变砖风险**：通过 12.0V 强电压门禁，极大保障了车辆熄火刷写期间的电源稳定性，防止 ECU 硬件损坏；
- **安全防篡改闭环**：SHA-256 端到端强校验防止了 CDN 缓存投毒与中间人篡改，保障固件二进制的绝对纯净；
- **业务连续性保证**：`SKIPPED_UNSAFE` 采用非阻塞设计，既守住了单车安全底线，又保证了大规模车队整体升级流水线的顺利推进；
- **系统开销可控**：前置检查借助 Redis 遥测热缓存完成，单车准入检查耗时 $< 1\text{ ms}$，对大规模并发调度吞吐无显著性能影响。
