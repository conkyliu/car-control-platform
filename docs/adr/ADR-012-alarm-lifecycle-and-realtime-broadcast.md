# ADR-012: 报警中心状态流转、WebSocket 广播机制与跨租户隔离决策

## 背景
车辆异常告警（如主电被拔断电、被盗拖移、SOS 紧急呼叫、超速）与电子围栏越界事件具有高时效性、责任敏感与多坐席协同等特征：
1. **协同冲突与责任追溯**：多个运营坐席或车队管理员同时监控告警大屏，若状态机定义含糊，容易产生重复处置、状态反复跳变或责任无法追溯的问题；
2. **实时性要求极高**：CRITICAL 级别的紧急告警必须在毫秒级推送给在线监控人员，轮询拉取无法满足时效要求；
3. **多租户安全底线**：在 SaaS 架构下，租户之间的车辆分布与报警事件高度机密，绝不能出现租户 A 的监控大屏接收到租户 B 的告警，或者利用告警 ID 跨租户越权查询与处置。

## 决策
1. **确定性单向终态有限状态机**：
   - 告警状态严格限定为三态：`PENDING`（待处理）为初始状态，`PROCESSED`（已处理）与 `IGNORED`（已忽略）为终态；
   - **终态单向不可逆**：一旦流转进入 `PROCESSED` 或 `IGNORED`，系统禁止将其逆转为 `PENDING`，亦禁止在两个终态间反复修改，杜绝责任推诿与并发冲突；
   - 状态流转必须强制记录操作人标识 (`processedBy`)、流转时间戳 (`processedAt`) 与处置备注 (`remark`)，并接入审计日志。
2. **多级 WebSocket 房间定向广播机制**：
   - 告警产生后通过 WebSocket 网关分发事件 `alarm:triggered`；
   - **严格禁止全服广播**，采用三级定向房间隔离：
     - `tenant:{tenantId}`：用于租户监控总览大屏；
     - `project:{projectId}`：用于指定车队/项目管理看板；
     - `vehicle:{vehicleId}`：用于单车详情与车控界面；
   - 客户端建立连接时必须携带合法 JWT，服务端鉴权后仅允许加入归属于该租户/项目的授权房间。
3. **数据层与服务层跨租户强隔离**：
   - 所有告警实体必须持久化 `tenant_id`、`project_id`、`vehicle_id` 与 `device_no`；
   - `AlarmRepository` 在查询列表、按 ID 查询、流转状态时，强制提取 `TenantContext` 注入 `tenant_id` 过滤条件；
   - 跨租户越权访问目标告警 ID 时直接返回 404（资源不存在）或抛出安全拦截异常，杜绝任何数据侧漏。

## 结果
- 告警从产生到处置形成闭环，权责清晰且具备完整可信审计链；
- 告警推送在毫秒级内精准投递给目标租户，消除轮询对后端的性能浪费；
- 形成“WebSocket 房间认证隔离 + DB 行级租户隔离”双重防线，彻底消除跨租户安全隐患。
