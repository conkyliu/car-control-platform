# ADR-011: 遥测数据冷热分离存储与 Douglas-Peucker 轨迹抽稀设计

## 背景
车联网控车平台具有典型的高频写入与读模式分化特征。以 10,000 辆在线车辆、每 5 秒上报一次 GPS 计算，云端面临持续 2,000+ QPS 的高并发遥测写入。业务查询表现为两类极端场景：
1. **实时位置读取（读多写多）**：监控大屏、手机 APP 首页状态卡片只需获取车辆当前最新的经纬度、速度与方向，要求亚毫秒级响应；
2. **历史轨迹回放（海量时序）**：车队管理者调取某车单日或多日行驶轨迹，点集规模达数千至数万个点。若直接将全量原始点透传给客户端，将导致 HTTP 报文体积数兆字节、移动端流量消耗大，且 Web 端 Leaflet / 高德地图瓦片图层由于 DOM 或 WebGL 节点过多而出现严重掉帧甚至崩溃。

## 决策
1. **建立三级存储分级体系 (Storage Tiering)**：
   - **热数据层 (Hot Tier)**：采用 Redis 内存存储（键名 `telemetry:latest:{vehicleId}`），高频覆盖写入，以 Sub-millisecond 延迟直接响应“车辆最新位置”查询与离线状态判定，完全卸载主关系数据库的读压力；
   - **温数据层 (Warm Tier)**：历史轨迹落入 PostgreSQL 分区表 (`telemetry_locations`)，按月份建立 Range 分区，联合索引键为 `(tenant_id, vehicle_id, recorded_at DESC)`，在线保留 90 天；
   - **冷数据层 (Cold Tier)**：超过 90 天的数据由定期离线任务导出为 Parquet 列式文件归档至对象存储 (S3 / OSS)，在线库通过 Drop Partition 快速释放空间。
2. **服务端权威 Douglas-Peucker 矢量抽稀**：
   - 在历史轨迹查询 API 内部执行服务端 Douglas-Peucker 分治几何抽稀，**严禁将未压缩的数万原始点直接推送到前端**；
   - 算法强制保留轨迹起点与终点，中间点根据预设容差阈值递归判定；
   - 默认容差设定为 `epsilon = 0.0001`（对应地面投影约 11 米），在忠实还原道路走向的前提下实现 80% ~ 90% 的数据压缩率，亦支持调用方按需指定精度容差。

## 结果
- 最新位置查询彻底与历史时序表解耦，读延迟稳定在 2ms 以内；
- 历史轨迹传输 Payload 体积缩减 80% 以上，显著节约带宽，前端地图回放稳定保持 60 FPS；
- 服务端抽稀算法经过 O(N log N) 递归分治优化，万点数据集计算耗时在 5ms 以内，性能损耗微乎其微。
